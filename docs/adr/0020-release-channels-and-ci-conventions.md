# ADR-0020: Release channels and CI conventions

- **Status:** Accepted; on 2026-09-27 Renovate (`.github/renovate.json`) took over the release workflow's SHA pins,
  the golangci-lint version and the goreleaser version, and `internal/buildconfig` checks that it still finds them;
  on 2026-09-27 every archive and the deb and rpm packages started to ship `THIRD_PARTY_NOTICES`, and CI and
  `make check` started to check the licences of the modules tent links (`internal/licenses`,
  [architecture §16](../architecture.md#16-technology-stack-and-releases)); go-licenses was not used because it
  misses modules linked only into the Windows binaries and NOTICE files, and as a tool in `go.mod` it would raise the
  versions of modules tent shares with it; amended by [ADR-0028](0028-tent-node-agent-units-and-delivery.md)
  (decision 1 and its M2 follow-up: tent-node joins the release in M2.5 as the bare binaries
  `tent-node_linux_amd64` and `tent-node_linux_arm64`, listed in `checksums.txt`, each with an SBOM, not
  notarized; one `THIRD_PARTY_NOTICES` covers both binaries and is also a file of the release, so not every copy
  carries it; the licence check and the CI snapshot cover tent-node)
- **Date:** 2026-09-25
- **Deciders:** ingvarch
- **Related:** [ADR-0006](0006-two-binaries-and-nodeconfig.md), [ADR-0011](0011-nomad-only-scope-and-licensing.md),

## Context

- [ADR-0013](0013-technology-stack.md) plans GoReleaser releases for M2, with `checksums.txt`, keyless cosign
  signatures and SBOMs, and CI with golangci-lint, `go vet`, `go test -race` and govulncheck.
- The maintainer asked to adopt the CI, lint and release conventions of their project urga now, in M0. urga ships a
  Homebrew cask, signed and notarized macOS binaries, and deb and rpm packages. These need an Apple Developer ID and a
  token for the tap repository, which ADR-0013 does not mention.
- ADR-0013 rules out testify-style assertion frameworks, which urga uses, and requires tests on both supported Go
  releases.
- The repository is private for now:
  - keyless signing writes the repository and workflow identity to the public Rekor transparency log;
  - brew cannot download release assets of a private repository;
  - on a private repository a macOS runner minute counts as ten Linux minutes, and a Windows minute as two.

## Decision

1. **tent is released with GoReleaser from M0**, on `v*` tags:
   - archives for linux, darwin and windows on amd64 and arm64: `tar.gz`, and `zip` on Windows;
   - `checksums.txt`, signed keyless with cosign into a `.sigstore.json` bundle;
   - an SBOM for every archive;
   - a Homebrew cask in `ingvarch/homebrew-tap`; a prerelease does not update it (`skip_upload: auto`);
   - macOS binaries signed with an Apple Developer ID and notarized;
   - deb and rpm packages that ship the licence;
   - release notes generated by GitHub; a tag like `v0.1.0-rc.1` is published as a prerelease (`prerelease: auto`).

   `tent-node` joins the release in M2, when `cmd/tent-node` exists, as raw linux amd64 and arm64 binaries
   (ADR-0013).
2. **No release while the repository is private.** The first step of the release workflow fails on a private
   repository: keyless signing would publish the workflow identity to the public Rekor log, and brew cannot download
   private assets.
3. **The release workflow pins every action by commit SHA**, with the version in a comment, because the job holds
   write permissions and every release secret. It needs these secrets:
   - `HOMEBREW_TAP_GITHUB_TOKEN`, to push the cask;
   - `MACOS_SIGN_P12`, `MACOS_SIGN_PASSWORD`, `MACOS_NOTARY_ISSUER_ID`, `MACOS_NOTARY_KEY_ID` and `MACOS_NOTARY_KEY`,
     to sign and notarize.
4. **CI** (`.github/workflows/ci.yml`):
   - runner images are pinned (`ubuntu-26.04`, `macos-15`, `windows-2025`), never `-latest`;
   - the Go version from `go.mod` builds the release, runs lint and govulncheck, and runs the tests on Linux, macOS
     and Windows, so the Go that builds the release is tested on every system the release ships for;
   - Linux also runs the tests with the newest Go (`stable`); macOS and Windows skip it because their minutes cost
     more on a private repository;
   - a release snapshot builds every archive and package on every pull request, without signing or notarization.
     `make dist` builds the same snapshot locally but does not check the goreleaser version, so the CI snapshot, with
     the version pinned in `.tool-versions`, is the reference;
   - CI also runs weekly, so govulncheck reports new advisories without a push; a new push to a pull request cancels
     its running checks; every job has a timeout.
5. **Config tests.** The tests in `internal/buildconfig` read the workflows, the Makefile and `.goreleaser.yaml`, and
   fail when they drift apart: the golangci-lint version, the test command, where Go comes from, the runner labels,
   the release targets and the action pins. `.gitattributes` keeps LF line endings on every system, so the tests read
   the files as committed on Windows too.
6. **Local checks.** `make check`, the default goal, runs fmt, lint, test and build. `make fmt` and `make lint` stop
   unless golangci-lint is at the version pinned in the Makefile, which is the version CI uses.
7. **Linters.** revive, gocritic and dupl run on top of ADR-0013's linters. `go vet` runs as golangci-lint's govet,
   not as a separate step.
8. **Differences from urga:**
   - no testify: the config tests use `testing`, go-cmp and `sigs.k8s.io/yaml` (ADR-0013);
   - two Go releases in the test matrix (ADR-0013);
   - cosign signatures and SBOMs, which urga does not have (ADR-0013).

## Consequences

### Positive

- The first release already has checksums, signatures, SBOMs and notarized macOS binaries.
- A broken release config fails the pull request that breaks it, not the next tag.
- When the workflows, the Makefile and the release config drift apart, a test fails.
- tent is tested on all three systems it ships for.

### Negative / trade-offs

- The Apple Developer membership, its certificate and notary key, and the tap token must be kept valid.
- GoReleaser publishes the GitHub release before it pushes the cask. If the tap push fails, the release is already
  public and the tap is behind it.
- The SHA pins in the release workflow are updated by hand until Renovate is set up.
- The newest Go is tested only on Linux, so a problem that shows up only with it on macOS or Windows goes unnoticed
  until `go.mod` moves to it.
- While the repository is private, the pipeline runs only as a snapshot.

### Follow-ups

- Before the first tag: make the repository public, set the six secrets, and ship third-party licence notices in the
  archives and packages.
- Once the repository is public:
  - a `release` environment that only `v*` tags can deploy to, holding the release secrets;
  - the full test matrix, since standard runners are free for public repositories.
- Renovate ([ADR-0013](0013-technology-stack.md)), which also updates the SHA pins.
- M2: `tent-node` joins the release.

## Alternatives considered

- **Keep releases in M2, as ADR-0013 planned.** The maintainer wants the pipeline proven early, and the snapshot on
  every pull request catches cross-platform breakage from the first commit.
- **No cask and no notarization.** Gatekeeper blocks binaries that Apple has not notarized, and brew is the main way
  to install tools on macOS.
- **testify, as in urga.** ADR-0013 rules out assertion frameworks.
- **The newest Go on macOS and Windows.** The release is built with the Go from `go.mod`, so that is the version that
  has to work on every system tent ships for.
- **All three systems with both Go releases.** It adds a macOS job and a Windows job, whose minutes count ten and two
  times on a private repository. Revisit once the repository is public.
