# Roadmap

> **Current status (2026-09-25):** M0 in progress. The skeleton has landed: the Go module, `tent version`, the Makefile,
> the layer rules in golangci-lint, the CI workflow and the release pipeline for `tent`.
>
> - Vultr is the first provider and the E2E platform ([ADR-0014](adr/0014-vultr-first-provider-and-e2e.md)).
> - Hetzner Cloud is second.
> - **Next:** the rest of M0 (API types, state store, spec commands), then M1. The Vultr spike has run
>   (2026-09-25); only its optional Object Storage check is open.
>
> Keep this file current: tick items as they land, and add a line to the log at the bottom when a milestone completes.

Each milestone ends in a state that can be demonstrated. A milestone is done when its **exit criteria** hold in CI
and, from M2 on, in the E2E suite on Vultr.

## Maintainer decisions

These come from [architecture §18](architecture.md#18-open-questions). All six were decided on 2026-09-25, so none
blocks M0 any more.

| # | Question | Decision |
|---|---|---|
| 1 | Label prefix and API group | `tent/` and `tent/v1alpha1` |
| 2 | Default `access.api` | `[0.0.0.0/0]` with mTLS + ACL, and a loud warning while it is open |
| 3 | Combined server+client mode | allowed for dev and small clusters through the `combined` role ([ADR-0019](adr/0019-combined-server-client-role.md)) |
| 4 | Default OS image | `ubuntu-24.04`; E2E also runs on `ubuntu-26.04` |
| 5 | Consul and Vault | out of v1 |
| 6 | Licence of tent | Apache-2.0 |

## M0 Foundation (no cloud)

**Goal:** a repository skeleton with the API, the state store and spec-only CLI commands, guarded by CI.

- [x] `go.mod` (`module github.com/ingvarch/tent`, `go 1.26`); packages follow the layout of
      [architecture §5](architecture.md#5-repository-layout-and-dependency-rules) as they are added
- [x] `LICENSE` (Apache-2.0) and a licence section in the README
- [x] `Makefile`: `build`, `test` (`-race`), `lint`, `fmt`, `generate`
- [x] `.golangci.yml` with depguard rules for the layering in [ADR-0021](adr/0021-import-rules.md): only
      `cmd/tent` imports provider packages, each cloud SDK stays in its provider, `tent-node` has no cloud code, and
      only `internal/nomadops` imports the Nomad API. `//nolint` needs a linter and a reason; library code does not
      panic.
- [ ] GitHub Actions CI: lint, tests with the `go.mod` Go on Linux, macOS and Windows and with the newest Go on Linux,
      a release snapshot and govulncheck; `internal/buildconfig` keeps the workflows, the Makefile and the release
      config consistent. The workflow is in place; tick this after its first green run.
- [ ] Renovate ([ADR-0013](adr/0013-technology-stack.md)) for Go modules and GitHub Actions, including the release
      workflow's SHA pins
- [x] `make check` (fmt, lint, test, build) and a golangci-lint version guard
- [x] Release pipeline for `tent` (GoReleaser, [ADR-0020](adr/0020-release-channels-and-ci-conventions.md)): archives,
      Homebrew cask with notarization, deb/rpm, cosign signatures, SBOMs
- [ ] Before the first release: make the repository public; set the secrets `HOMEBREW_TAP_GITHUB_TOKEN`,
      `MACOS_SIGN_P12`, `MACOS_SIGN_PASSWORD`, `MACOS_NOTARY_ISSUER_ID`, `MACOS_NOTARY_KEY_ID`, `MACOS_NOTARY_KEY`;
      and ship third-party licence notices (for example generated by go-licenses) in the archives and packages
- [x] `internal/buildinfo` (version, commit and date via ldflags) and `tent version`
- [ ] `api/v1alpha1`:
  - [ ] `Cluster` and `NodeGroup` types with JSON tags, following
        [architecture §3](architecture.md#3-domain-model-and-api). The provider enum covers `vultr` and `hetzner`,
        with provider-specific blocks.
  - [ ] The role enum: `server`, `client`, `combined` ([ADR-0019](adr/0019-combined-server-client-role.md)).
  - [ ] Defaults, idempotent: `Default(Default(x)) == Default(x)`. `access.api` defaults to `[0.0.0.0/0]`;
        `nomad.clientIntroduction` defaults to `strict`, or `warn` when the cluster has a `combined` group.
  - [ ] Validation with field paths: names, CIDRs, zones ⊆ cluster zones, `zones == [region]` for Vultr, exactly
        one `server` or `combined` group of size 1/3/5, no `strict` client introduction with a `combined` group, and
        so on.
  - [ ] Strict YAML decoding of multi-document files.
  - [ ] JSON Schema generation (`make generate`).
- [ ] `internal/statestore`:
  - [ ] the `Store` interface and a conformance test suite shared by all backends;
  - [ ] a `file://` backend;
  - [ ] an `s3://` backend (aws-sdk-go-v2 with a custom endpoint; tested against MinIO in CI);
  - [ ] cluster layout helpers and the `tent-version` guard;
  - [ ] lease locking: conditional put, then `flock`, then best-effort, in that order; `tent state unlock --force`.
- [ ] `internal/cli`:
  - [x] the root command;
  - [ ] global flags `--state`/`TENT_STATE`, `--name`/`TENT_CLUSTER`, `-o`, `-v`, `--log-format` (`-o` is done; the
        rest comes with the state store and the commands);
  - [ ] a config file that holds defaults only.
- [ ] Commands, for the spec only at this point:
  - [ ] `create cluster` (generator flags) and `create -f`
  - [ ] `get clusters|nodegroups [--full]`
  - [ ] `edit cluster|nodegroup` (validate and show a diff before saving)
  - [ ] `replace -f`
  - [ ] `delete cluster` (state only for now)

**Exit criteria:**
- Lint and tests are green in CI.
- A spec survives `create → get -o yaml → replace` unchanged.
- Invalid specs produce field-path errors.
- Two concurrent mutating commands on the file backend are serialized.

## Spike: Vultr unknowns (before M1)

**Goal:** replace every 🔬 item in [platform notes §3](platform-notes.md#3-vultr) with a measured fact, and resolve the
provisional parts of [ADR-0018](adr/0018-vultr-provider-design.md). How to run it:
[`hack/vultr-spike/README.md`](../hack/vultr-spike/README.md).

- [ ] Account prepared (before wiring E2E into CI):
  - [ ] a dedicated account or IAM service user (the spike used a key with full account access);
  - [ ] API key IP allow-list;
  - [ ] instance limit ≥ 8 requested (3 concurrent instances worked on 2026-09-25).
- [x] `hack/vultr-spike/spike.sh --preflight`: region, plans and image resolution without an API key.
- [x] Runs in `ams` on 2026-09-25: `tt3s1g` (v1), `hh7sgs` (v2) and `mqlko4` (v2, boot only). Results are in
      [platform notes §3.16](platform-notes.md#316-spike-runs-2026-09-25):
  - [x] maximum `user_data` size, for both PATCH and create: no API limit up to 4 MiB; 64 KiB works end to end;
  - [x] tag syntax and filter semantics: verbatim storage; exact but case-insensitive filter; a new instance is
        listable by tag at once;
  - [x] ownership markers in description and name fields: stored verbatim;
  - [x] accepted VPC masks (`/16`, `/20`, `/24` all accepted), interface name (`enp8s0`), MTU 1450, static netplan;
  - [x] boot timings: cloud-init done 129–149 s after the create call; vendor data no longer upgrades packages;
  - [x] the default host firewall: ufw, deny incoming, only 22/tcp allowed, so Nomad ports are blocked on the VPC too;
  - [x] firewall groups do not filter VPC traffic;
  - [x] alias IPs in the VPC are reachable from other instances;
  - [x] the metadata service serves user data updated by PATCH within 4 s, and cloud-init does not re-run after a
        restart;
  - [x] `halt` is a hard power-off, and `start` works;
  - [x] the VPC delete fails for 14–20 s after its instances are gone;
  - [ ] optional: `If-None-Match` / `If-Match` on Vultr Object Storage: not run (needs a bucket; Standard is
        $18/month).
- [x] Record the verified results in `docs/platform-notes.md` §3, and mark the resolved ADR-0018 items on its status
      line.
- [x] **Spike v2**, fixing what broke the SSH-dependent checks, then re-run the inconclusive checks:
  - [x] one SSH connection per host (ControlMaster), `IdentitiesOnly`, `-F /dev/null`, and polling at most once
        every 15 s;
  - [x] "unknown (ssh failed: reason)" instead of negative results; circuit breaker per host;
  - [x] check the `start` response and power state after `halt`;
  - [x] fix the self-matching `pgrep` guard of the test listener (the listener is now a systemd unit);
  - [x] collect data from inside the instance, once from user_data `runcmd` and once over SSH:
    - [x] ufw, iptables/nft, fail2ban and sshguard status, `sshd -T`;
    - [x] `cloud-init analyze` and `systemd-analyze blame`;
    - [x] the vendor data, with secrets redacted.
  - [x] find out where the ~6 minutes of first boot go: nowhere. On the instance, cloud-init finishes 32–37 s after
        kernel start. The long figures came from the measurement.

## M1 Vultr infrastructure

**Goal:** tent creates and deletes the cloud side of a cluster on Vultr, empty VMs included, with a correct plan.

- [ ] A govultr client wrapper:
  - [ ] automatic retries off for non-idempotent calls;
  - [ ] a tent-side token bucket (10 requests/s) that honours `Retry-After`;
  - [ ] typed errors (not found, rate limited, limit reached, invalid).
- [ ] The label codec (canonical labels ↔ instance tags; markers in free-text fields), chosen from the spike
      results.
- [ ] `internal/engine`:
  - [ ] `Task`, `Key`, the graph and cycle detection;
  - [ ] plan, parallel apply and error aggregation;
  - [ ] diff rendering, `-o json` and `--exit-code`.
- [ ] `internal/model`: intents for the network, access rules, node groups and the join strategy (seed and refresh).
- [ ] Vultr inventory: instances filtered by the cluster tag on the server side; VPCs, firewall groups and SSH keys
      filtered on the client by marker; a dedupe pass ([ADR-0015](adr/0015-idempotency-without-unique-names.md)).
- [ ] Vultr tasks, each with an "apply → re-plan → no-op" test:
  - [ ] SSH key;
  - [ ] VPC;
  - [ ] firewall groups (`servers`, `clients`).
- [ ] Vultr `Nodes`:
  - [ ] create with an operation id and search-before-retry;
  - [ ] readiness polling (`active` / `running` / `ok`);
  - [ ] VPC IP and MAC lookup;
  - [ ] hard stop and delete;
  - [ ] list;
  - [ ] user data scrub (`MutableUserData`; confirmed by the spike).
- [ ] An availability preflight (`/v2/regions/{id}/availability`) and verbatim account-limit errors.
- [ ] `update cluster`: infrastructure plus node counts, no Nomad yet; VMs boot a placeholder user data.
- [ ] `delete cluster`: full cleanup by markers in dependency order, with retries (the VPC delete fails for about
      20 s after its instances are gone).
- [ ] A fake govultr (service interfaces), golden plan tests, and interruption and lost-response tests.

**Exit criteria:**
- `tent update cluster --yes` creates the VPC, the firewall groups and N empty VMs on Vultr, and a re-run is a no-op.
- A simulated lost create response never produces a duplicate VM.
- `tent delete cluster --yes` leaves nothing that carries the cluster markers.

## M2 Nomad bootstrap

**Goal:** a working, secured Nomad cluster on Vultr with a running job.

- [ ] `internal/pki`:
  - [ ] the CA bundle;
  - [ ] per-node certificates with `serverAuth` and `clientAuth` (combined nodes get both Nomad names);
  - [ ] operator certificates;
  - [ ] the gossip key;
  - [ ] the bootstrap secret.
- [ ] `internal/assets`:
  - [ ] the Nomad release download, with `SHA256SUMS` verified against the embedded HashiCorp key;
  - [ ] the CNI plugins;
  - [ ] tent-node checksums taken from the release.
- [ ] `internal/channels`: the embedded `stable` channel, with images per provider.
- [ ] `internal/nodeconfig`:
  - [ ] the `NodeConfig` types;
  - [ ] Nomad config rendering (`00-tent.hcl`, `05-join.hcl`, `10-node.hcl`, `99-user.hcl`) with golden tests,
        including a `combined` agent with both blocks;
  - [ ] the semantic spec hash;
  - [ ] a size-budget test against `MaxUserDataBytes`.
- [ ] `tent-node`:
  - [ ] phases `preflight`, `system`, `hostfirewall` (take over from ufw/firewalld), `runtime`, `cni`, `join`,
        `nomad`, `verify`;
  - [ ] the Vultr `Environment`;
  - [ ] the systemd units: `tent-node.service` and `tent-node-join.timer`;
  - [ ] the `install`, `up` and `refresh-join` commands.
- [ ] `internal/nomadops`:
  - [ ] client construction (mTLS, `TLSServerName`, in-memory PEM);
  - [ ] ACL bootstrap with the pre-generated secret and a `token/self` check;
  - [ ] intro tokens;
  - [ ] leader and health checks.
- [ ] The flow: `server-0` → the other servers, seeded → leader → ACL bootstrap → intro token per client → clients,
      seeded → user data scrub.
- [ ] `validate cluster [--wait]`, `export nomad`, `ui`.
- [ ] `tent-node` in the release (linux amd64/arm64 raw binaries), and a `hack/` dev upload of tent-node to a
      presigned URL.
- [ ] The E2E harness on Vultr, the `smoke` and `security` scenarios, and the janitor (tag-based). `smoke` also
      runs on `ubuntu-26.04`.
- [ ] A loud warning in `validate` and mutating commands while `access.api` is open to the internet, and for
      `combined` clusters.

**Exit criteria:** E2E `smoke` passes on Vultr.
- A docker job with a service runs.
- `delete` leaves nothing behind.
- Containers cannot reach the metadata endpoint.
- A client without an intro token is rejected.

## M3 Day-2 operations

- [ ] `internal/rollout`: pure decision functions with golden operation sequences.
- [ ] Combined nodes roll like servers and are drained first; an E2E scenario with a `combined` group.
- [ ] Server rolling update, following [ADR-0017](adr/0017-api-driven-server-removal.md):
  - [ ] surge with a seed list;
  - [ ] autopilot health (handle HTTP 429);
  - [ ] leadership transfer;
  - [ ] hard stop, then peer removal and `force-leave` with prune;
  - [ ] the join refresh wait.
- [ ] Client rolling update:
  - [ ] surge;
  - [ ] mark ineligible and drain with a deadline;
  - [ ] delete and purge;
  - [ ] honour `maxSurge` and `maxUnavailable`.
- [ ] Scale down with drain; server group resize 1 ↔ 3 ↔ 5.
- [ ] `upgrade cluster` from channels, enforcing servers before clients.
- [ ] `backup create|restore`.
- [ ] E2E `ha`:
  - [ ] a probe runs during the roll;
  - [ ] after every server has been replaced, restart a client and assert that it rejoins.
- [ ] E2E `upgrade`.

**Exit criteria:** E2E `ha` and `upgrade` pass on Vultr, with no quorum loss and no job downtime beyond the configured
migrations.

## M4 Hetzner provider

Implemented once a Hetzner account can create servers reliably (limits raised, no creation restrictions).

- [ ] An hcloud client wrapper:
  - [ ] a RoundTripper that throttles on `RateLimit-*`;
  - [ ] `WithPollOpts` with exponential backoff;
  - [ ] `Action.WaitFor` batching.
- [ ] Hetzner inventory by label selectors, and the label codec (native labels).
- [ ] Hetzner tasks: SSH key (adopt by fingerprint), network and subnets, firewalls, placement groups in shards of
      ≤ 10.
- [ ] Hetzner `Nodes`:
  - [ ] create powered off, attach (`ip` for server slots, `ip_range` for clients), power on;
  - [ ] ACPI shutdown (`GracefulShutdown`);
  - [ ] delete.
- [ ] A fixed-slot `JoinStrategy` ([ADR-0009](adr/0009-server-discovery-fixed-ip-slots.md)).
- [ ] A Hetzner lock (the `<cluster>-lock` firewall mutex).
- [ ] The Hetzner `Environment` for tent-node.
- [ ] The same E2E suite on Hetzner, plus `arm` (CAX) and location-spread HA (fsn1/nbg1/hel1).

## M5 Provider polish

- [ ] An optional API load balancer (Vultr: public with firewall rules and ID-based membership; Hetzner: label
      selectors), and ingress groups (80/443).
- [ ] DNS records: Vultr DNS and the Hetzner Zones API (optional).
- [ ] `tent cost`, with costs shown in plans.
- [ ] CSI addons: vultr-csi (official Nomad docs) and hcloud-csi.
- [ ] Private topology: Vultr `vpc_only` + managed NAT gateway; Hetzner NAT node + route + internal load balancer.
- [ ] `toolbox dump`.

## M6 AWS provider

- [ ] VPC, subnets per AZ, IGW/NAT, and Security Groups (including the intra-cluster intents).
- [ ] EC2 through `Nodes` first; ASG-managed groups once the bootstrap controller exists.
- [ ] The cloud auto-join `JoinStrategy` and the IMDSv2 `Environment`.
- [ ] The same E2E suite on AWS.

## Later

- The bootstrap controller, with CSR and cloud identity verification ([ADR-0008](adr/0008-node-credential-delivery.md)).
- Autoscaling and automatic replacement of failed nodes (an in-cluster controller and Nomad Autoscaler integration).
- Consul and Vault as optional components.
- CA rotation, and `age` encryption of secrets at rest.
- An OpenTofu/Terraform export target.
- Nomad multi-region federation, which is also the answer to Vultr's single failure domain.
- Bare-metal clients through Hetzner vSwitch subnets.
- An in-place Nomad upgrade strategy.
- A local VM provider (QEMU/Incus) for fast core tests without a cloud.
